**Project:** B.Tech final year project, Group GC19, Department of Computer Engineering, Pimpri Chinchwad College of Engineering, Pune.
**Paper:** "A Compliance-Aware Multilingual Voice Assistant for Banking and Finance" (CCIT 2026).
**Audience for this build:** a live demo in front of a review panel and a conference audience.

## 1. Mission

Build a working, runnable demo of the system described in the attached paper and synopsis. A person must be able to open a browser, speak to the assistant in English, Hindi, Marathi or a mix of them, and get a spoken answer back. Behind that conversation, every stage must write an inspectable record, and a second screen must show a compliance officer exactly how the system reached its decision.

The point of the demo is not to look like a chatbot. Plenty of chatbots exist. The point is to make **auditability visible**. If a viewer cannot watch a decision being made and verify it afterwards, the demo has failed even if the speech recognition is perfect.

Two things must be true at the end:

1. The assistant talks and follows requests.
2. Every claim the paper makes about compliance is demonstrable on screen in under ten minutes.

## 3. Hard constraints

- **Runs offline on a laptop CPU.** No paid API keys, no GPU assumed. If a GPU is present, use it, but never require it. The review room WiFi will be bad.
- **No real personal data, ever.** All accounts, customers, transactions and voices are synthetic and generated by a seed script. Put a banner in the UI saying so.
- **No real banking integration.** The core banking layer is a mock service with a documented interface.
- **Cold start under 60 seconds** after `make demo`. Models must be pre-downloaded by a setup script, not fetched at launch.
- **Text fallback path.** Microphones fail in review rooms. Every voice interaction must also be drivable by typing. The pipeline after ASR is identical so the demo survives a dead mic.
- **Honesty registry.** Every component declares itself `REAL`, `BASELINE` or `SIMULATED` in one central file, and the dashboard renders that status. Do not let the demo imply a capability it does not have. See section 9.

## 6. The spine: ComplianceTrace

This is the most important design decision in the build. The paper claims compliance is architectural rather than bolted on. That claim has to be true in the code, and this object is how.

One `ComplianceTrace` is created per turn and threaded through every stage. Each stage **appends** and never overwrites. At the end of the turn the trace is serialised, PII-redacted, hashed and appended to the ledger. The dashboard renders the trace directly. The audit is a query over traces, not a reconstruction.

```python
class StageRecord(BaseModel):
    stage: str                 # "asr" | "langid" | "nlu" | "retrieval" | ...
    started_at: datetime
    duration_ms: float
    inputs_digest: str         # sha256 of stage input, not the input itself
    outputs: dict              # stage-specific, must be JSON-serialisable
    confidence: float | None
    model_id: str | None       # name + version + revision hash
    capability: Literal["REAL", "BASELINE", "SIMULATED"]
    notes: str | None

class ComplianceTrace(BaseModel):
    trace_id: UUID
    session_id: UUID
    turn_index: int
    consent_ref: UUID
    stages: list[StageRecord] = []
    language_spans: list[LanguageSpan] = []
    intent: str | None
    intent_confidence: float | None
    slots: dict = {}
    retrieved: list[RetrievedPassage] = []
    risk_score: float | None
    risk_tier: int | None
    risk_components: dict = {}      # every term of R, for the dashboard
    auth: AuthOutcome | None
    decision: Literal["automated", "refused", "escalated"] | None
    decision_reason: str | None
    action_taken: str | None
    agent_id: str | None
    pii_tokens: dict = {}           # token -> type, never the raw value
```

Rule to enforce in code review: **no stage may return a value that is not recorded in the trace.** If a number influences a decision, it is in `risk_components` or `outputs`. A reviewer should be able to recompute the decision from the trace alone. Write a test that asserts this for the risk score.

## 7. Algorithms

Implement these properly. Do not stub them. Write `docs/ALGORITHMS.md` explaining each one with its formula, complexity and the parameter values you chose, because this document feeds directly into the next paper.

### A1. Code-switch-aware language identification

Per-word language posteriors from ASR are noisy and flip mid-sentence. Smooth them with Viterbi over a language state machine with a switch penalty, so the tagger produces coherent spans instead of alternating labels.

States are the supported languages. For word `i` with posterior `p_i(l)`:

```
score(i, l) = log p_i(l) + max over l' [ score(i-1, l') - eta * 1[l != l'] ]
```

`eta` is the switch penalty. Start at `eta = 2.0` and tune on the eval set. Backtrack for the best path, then merge consecutive same-language words into `LanguageSpan` objects.

Report the code-mix index per utterance:

```
CMI = 100 * (1 - max_l(n_l) / n_total)    for n_total > 0
```

`CMI = 0` is monolingual. Show it in the dashboard for beat 4. This is a genuine contribution worth writing up: most pipelines run language ID once per call, and the paper argues code-mixing should be the normal case.

Complexity `O(n * |L|^2)`, trivial at utterance length.

### A2. Confidence fusion

One weak signal should be able to veto automation, so combine geometrically rather than by weighted average. An average lets a confident intent hide a terrible transcript.

```
c_final = c_asr^alpha * c_intent^beta * c_retr^gamma      alpha + beta + gamma = 1
```

Use `c_retr = 1` for intents that do not need retrieval. Defaults `alpha = 0.3, beta = 0.45, gamma = 0.25`. Put them in `config.py` and surface `c_final` in the trace.

### A3. Intent classification and slot extraction

Embed the utterance with the multilingual sentence-transformer, classify with a logistic-regression head trained on the seeded utterance set. Softmax posterior gives `c_intent`.

Intents, from the paper: `get_balance`, `mini_statement`, `cheque_status`, `branch_ifsc`, `product_info`, `block_card`, `limit_change`, `add_payee`, `fund_transfer`, `apply_loan`, `dispute_txn`, `fraud_report`, `agent_request`, `out_of_scope`.

Seed at least 25 utterances per intent across English, Hindi, Marathi and code-mixed forms. `out_of_scope` needs the most and the widest variety, because it is what protects the refusal path.

Slots by rule, not by model: amount (with Indian numbering words, "fifty thousand", "pachas hazaar"), account last-4, card last-4, payee name, date range, cheque number. Rules are auditable, which is the point.

### A4. Retrieval grounding with an explicit refusal path

Chunk the policy KB by heading, embed, store with `doc_id`, `version`, `effective_date`, `section`.

1. Embed query, cosine against all chunks.
2. Apply MMR for diversity so three near-identical chunks do not fill the top-k:
   `MMR = argmax_d [ lambda * sim(d, q) - (1 - lambda) * max_{d' in S} sim(d, d') ]`, `lambda = 0.7`.
3. Keep top-k (`k = 4`) above the similarity floor `delta`.
4. **If nothing clears `delta`, refuse.** Do not generate. Set `decision = "refused"`, record the max score achieved, offer a human agent.

Calibrate `delta` on the eval set: pick the value maximising F1 between answerable and unanswerable queries. Start at `0.42` for this embedding model and report the tuned value. Every answer cites `doc_id` and `version` in the trace and says the source aloud in the spoken reply.

### A5. Risk scoring and tier assignment

Straight from the synopsis:

```
R = w1*sens(intent) + w2*norm(amount) + w3*(1 - s_verify) + w4*dev(history)
sum(w) = 1,  defaults w = (0.40, 0.25, 0.25, 0.10)
```

- `sens(intent)` from a lookup table in `config.py`, range 0 to 1. `product_info = 0.05`, `get_balance = 0.35`, `block_card = 0.70`, `fund_transfer = 0.85`, `fraud_report = 1.0`.
- `norm(amount) = min(1, log1p(amount) / log1p(A_max))`, `A_max = 200000`. Log scale because the jump from 1k to 10k matters more than 190k to 200k.
- `s_verify` is the speaker verification score in 0 to 1, or 0 when no verification has run.
- `dev(history) = 1 - exp(-lam * anomalies)`, `lam = 0.5`. Count anomalies as: new device, unusual hour, first-ever payee, rapid repeat attempts.

Tier from cut-points `t1 = 0.25, t2 = 0.50, t3 = 0.75`, **plus hard overrides that bypass the score entirely**: `fraud_report`, `dispute_txn` and `agent_request` are always tier 3. A scoring bug must never be able to automate a fraud report.

**Session tier ratchet.** Within a session the tier is monotonically non-decreasing. Once a conversation has been escalated it cannot silently de-escalate on the next turn. This prevents an attacker from lowering their own risk by asking an innocent question after a refused transfer, and it is a clean safety property to state in the paper.

Automate only when **all** hold: `R < t_tier`, `c_final >= tau_tier`, verification passed if the tier requires it, and retrieval cleared `delta` if the intent needs grounding. Otherwise refuse or escalate. `tau` rises with tier: `(0.50, 0.62, 0.75, 1.01)`, where tier 3 is unreachable by design.

Tier behaviour:

- **Tier 0** public information, no authentication.
- **Tier 1** account-specific, passive speaker verification.
- **Tier 2** transactional, verification plus OTP plus spoken read-back before the action commits.
- **Tier 3** human handover, mandatory, with the context packet.

### A6. Speaker verification and anti-spoofing

Enrolment: three utterances, mean of L2-normalised ECAPA embeddings.

Verification: `s = cos(x_e, x_t)`, accept above `theta`. Choose `theta` at the Equal Error Rate on the synthetic trial set and **report the actual EER number**, do not assert a value.

Anti-spoofing needs care. A trained AASIST model is out of scope for this demo, and claiming one would be dishonest in a review. Do this instead:

- Define the interface `AntiSpoofScorer.score(audio) -> float` so a real countermeasure can drop in later.
- Ship an LFCC + GMM baseline trained on the synthetic bona fide set versus TTS-generated spoofs you create with Piper. This is a real, classical, defensible baseline.
- Register it as `BASELINE`, not `REAL`, in the capability registry, and label it that way in the dashboard.
- Feed the score into `s_verify` as the paper specifies: `s_verify = s_cos * spoof_score`, so a suspected spoof drags the verification term down and raises `R`.

Report the tandem detection cost function `t-DCF` alongside EER, since the synopsis commits to it.

### A7. PII redaction before persistence

Runs **before** anything touches disk. Raw audio lives in memory only for as long as transcription needs it, then is dropped. Write a test asserting no raw audio file exists after a turn completes.

Detect and tokenise: PAN (`[A-Z]{5}[0-9]{4}[A-Z]`), Aadhaar (12 digits **validated with the Verhoeff checksum**, so random 12-digit strings are not false positives), card number (**Luhn validated**), account number, phone, email, and spoken digit sequences that ASR produced as words.

Replace with `<PAN_1>`, `<ACCT_2>` and so on. Keep the mapping in a per-session vault encrypted with AES-256-GCM, held separately from the transcript store. Implement Luhn and Verhoeff yourself in `pii.py`; both are short and both are genuine algorithms worth having in the report.

Consent withdrawal must purge the vault and the transcripts for that session, and append a purge record to the ledger. Demonstrate that in the dashboard.

### A8. Tamper-evident ledger

```
H_i   = SHA256( H_{i-1} || canonical_json(M_i) || t_i )
sig_i = HMAC-SHA256( key, H_i )
```

Canonical JSON means sorted keys and fixed separators, otherwise verification is non-deterministic and the whole thing is worthless. Genesis `H_0` is a fixed constant recorded in config.

Store a checkpoint hash every `k = 64` records. Then:

- **Full verify** is `O(n)`.
- **Tamper localisation** is `O(log n) + O(k)`: binary search the checkpoints for the first failing segment, then scan linearly inside it to name the exact record.

Expose `POST /ledger/verify` returning `{ok, records_checked, first_broken_index, broken_record_id, expected_hash, actual_hash}`.

`scripts/tamper_demo.py` edits one field of one record directly via SQL for beat 10. The dashboard must then show red and name that record. This single feature demonstrates the paper's central claim better than any slide.

### A9. Evaluation metrics

- **WER** `= (S + D + I) / N` from Levenshtein alignment. Implement the alignment, do not import a one-liner, since you need the alignment for the next metric anyway.
- **Entity-level error rate** `EER_s = (1/|E|) * sum_i 1[e_hat_i != e_i]` over financial entities. Use the WER alignment to map reference entity spans onto hypothesis tokens, then compare. Report per entity type: account number, amount, payee, product name. This is the headline evaluation claim of the paper, so it must be computed honestly and reported even when it looks bad.
- **Recall@k** for retrieval, and the tuned `delta`.
- **Speaker EER** and **t-DCF**.
- **Latency** per stage, p50 and p95, from the trace timings.

`make eval` runs the harness over `data/eval/` and writes `docs/RESULTS.md` with a table per metric. Keep the eval set small and honest: 40 to 60 utterances, hand-labelled, spread across the four languages and the intent set. State the set size next to every number.

## 10. Build phases

Work in this order. Each phase ends with something runnable, and with its acceptance test passing. Do not begin a phase until the previous one is green.

**P0. Skeleton.** Repo, Makefile, FastAPI boot, React boot, `ComplianceTrace`, `capabilities.py`, config with every threshold named. `make demo` serves an empty console.
*Accept:* `GET /capabilities` returns the registry; a trace with zero stages round-trips through the API.

**P1. Ledger first.** Build A8 before the voice pipeline. Everything else writes into it, so it must be stable early.
*Accept:* 1000 synthetic records verify in `O(n)`; corrupting record 437 is localised correctly; corrupting the last record is caught; checkpoint search matches linear search on 20 random corruptions.

**P2. Text pipeline end to end.** `POST /turn/text` through NLU, retrieval, risk, decision, ledger. No audio at all yet.
*Accept:* all ten demo beats pass in text form, driven by a pytest scenario file. This is the safety net for the live demo.

**P3. Voice in.** VAD, ASR, code-switch language ID, confidence fusion. WebSocket streaming with partial transcripts.
*Accept:* code-mixed utterance from beat 4 produces correct spans and a non-zero CMI; p95 ASR latency under 2s for a 6s utterance on CPU.

**P4. Voice out.** Piper TTS, language selected from the dominant span, streaming playback.
*Accept:* full spoken round trip under 4s p95; reply language matches query language.

**P5. Security.** Speaker enrolment and verification, anti-spoof baseline, PII redaction, RBAC, encryption at rest.
*Accept:* verification EER measured and written to `RESULTS.md`; no raw audio on disk after a turn; a `customer` token is refused on `/ledger/export`; account digits never appear in the stored transcript.

**P6. Dashboard.** Trace view, live stage timeline, risk component breakdown, retrieval citations, ledger panel with verify and tamper localisation, escalation queue, capability legend.
*Accept:* beats 9 and 10 are performable entirely from the UI by someone who has not seen the code.

**P7. Evaluation and docs.** Metrics harness, `RESULTS.md`, `ALGORITHMS.md`, `ARCHITECTURE.md`, `DEMO_RUNBOOK.md`, architecture and sequence diagrams.
*Accept:* `make eval` regenerates every number in `RESULTS.md` from scratch.

## 14. Rules on honesty

The review panel will ask hard questions. These rules keep the answers easy.

- Never print a metric the harness did not compute. No placeholder accuracy numbers anywhere in the UI or docs.
- Where the synopsis quotes literature figures (15 to 20 percent WER on Earnings-21, up to 72 percent phoneme error reduction from cross-lingual pre-training), label them as literature values, not as measurements of this system.
- The ASR is not fine-tuned on banking audio in this demo. Say so in the capability note and in `RESULTS.md`. The entity-level error rate you measure is the **baseline** the fine-tuned model must beat, and framing it that way is a stronger story than pretending otherwise.
- The anti-spoof component is a classical baseline, not AASIST.
- Do not use em dashes in any user-facing string, comment or document. Use plain punctuation.
