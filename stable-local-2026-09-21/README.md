# Compliance-Aware Multilingual Voice Assistant for BFSI

B.Tech final year project, Group GC19, Department of Computer Engineering,
Pimpri Chinchwad College of Engineering, Pune.

A working demo of the system described in "A Compliance-Aware Multilingual
Voice Assistant for Banking and Finance" (CCIT 2026). A person speaks to it in
English, Hindi, Marathi or a mixture of the three, and gets a spoken answer
back. Behind that conversation, every stage of every turn writes an
inspectable record, and a second screen shows a compliance officer exactly how
the system reached its decision.

> **All data in this system is synthetic.** Customers, accounts, cards,
> transactions and enrolled voices are generated by a seed script from a fixed
> random seed. No real personal data is present and no real banking system is
> connected.

## The point

Plenty of banking chatbots exist. The thing being demonstrated here is not
that it talks, it is that **auditability is architectural**. A single
`ComplianceTrace` object is created per turn and threaded through every stage;
stages append to it and never overwrite. At the end of the turn it is
redacted, hashed and appended to a tamper-evident ledger. The audit is a query
over those traces, not a reconstruction after the fact.

The sharpest demonstration of that is a presenter editing one stored record
with raw SQL in front of the audience, clicking Verify, and watching the chain
go red and name the exact record.

## Quick start

```
make setup      # venv, Python dependencies, npm install. Needs network, once.
make models     # pre-download every model. Needs network, once.
make seed       # synthetic data, intent head, KB index, enrolled voices
make demo       # backend on :8000, frontend on :5173
```

Then open `http://127.0.0.1:5173/` for the customer console and
`http://127.0.0.1:5173/compliance` for the compliance dashboard.

Runs on a laptop CPU, offline, with no paid API keys. A GPU is used if present
and never required.

```
make test       # the full suite, including all ten demo beats in text form
make eval       # regenerates docs/RESULTS.md from scratch
make tamper     # corrupt one ledger record, for demo beat 10
make restore    # undo it
make diagrams   # regenerate the figures
```

A `Dockerfile` and `docker-compose.yml` provide an optional single-container
path. The host path above is faster to start and is what the runbook assumes.

## What the build found

Things that only showed up once it was running, all measured and all written
down in `docs/ARCHITECTURE.md` section 6b and `docs/RESULTS.md`:

- A monolingual knowledge base with one global similarity floor systematically
  refuses non-English speakers. An answerable question scores 0.72 in English
  and 0.31 in Marathi, so the calibrated floor turns away 0 of 2 Marathi
  queries it answers in English. That undercuts the project's own inclusion
  argument and belongs in the paper as a result.
- An anti-spoof baseline trained with band-limited bona fide audio against
  clean spoof audio learns "wideband means spoof". It scored a clean recording
  of the enrolled speaker at 0.02. Both classes now share a channel.
- Channel mismatch, not the model, is the practical limit on speaker
  verification: 0.94 for a matched channel against 0.50 for clean audio from
  the same speaker, with a threshold near 0.76.
- The specified risk formula makes tier 0 unreachable and lets a verified
  caller skip the read-back on a card block. Both are resolved and both
  resolutions are argued in `docs/ARCHITECTURE.md` conflict C9.

## Honesty

`backend/app/capabilities.py` is the single source of truth for what is real
in this system. Every component declares itself `REAL`, `BASELINE` or
`SIMULATED`, the pipeline stamps that status onto each trace stage, and the
dashboard renders it. A panel member who asks "is that actually working?" gets
the answer off the screen.

The three that are not `REAL`:

- **anti-spoofing** is `BASELINE`, a classical LFCC and GMM countermeasure,
  not a trained AASIST model
- **core banking**, **OTP delivery** and the **agent console** are `SIMULATED`

The ASR is not fine-tuned on banking audio in this build. The entity-level
error rate measured in RESULTS.md is therefore the baseline a fine-tuned model
has to beat, and is reported as such.

No metric appears anywhere in this repository that `make eval` did not
compute.

## Layout

```
backend/app/
  trace.py          the ComplianceTrace, the spine of the system
  capabilities.py   the honesty registry
  config.py         every threshold and weight, no magic numbers inline
  turn.py           the turn orchestrator
  pipeline/         vad, asr, langid, nlu, slots, retrieval, dialogue, tts
  security/         speaker, antispoof, pii, rbac, ledger, crypto
  banking/          mock core banking and one action per intent
  eval/             metrics and the harness behind `make eval`
frontend/src/
  routes/           Customer.tsx and Compliance.tsx
  components/       TraceView, LedgerPanel, CapabilityLegend
data/
  policy_kb/        15 versioned policy documents with YAML front matter
  seed/             the intent utterance bank and generated voices
  eval/             the hand-labelled evaluation set
scripts/            download_models, seed_data, make_eval_set, tamper_demo, diagrams
```
